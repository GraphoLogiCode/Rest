# Rest on ECS Express Mode — Ohio

The app, authenticated API, reviewed catalog, preference recommendation engine and real-photo journal run together at an AWS-managed HTTPS URL. Supabase remains the account/database service. Nothing in this deployment requires the Mac to remain on. It contains no generated product-outcome model: that feature remains unavailable until validated outcome data and a model exist.

This replaces the App Runner launch instructions. Use the direct CLI workflow below; the former CloudFormation templates are archived under `deploy/pilot/legacy-apprunner/` and are not used by this workflow.

## Prepared and verified

- `settings.json` fixes the account, Ohio region, bucket, repository, cluster, service, task family, log groups, secret name and role names. Change settings only with matching policy regeneration and review.
- Four roles: a human deployment role, CodeBuild role, ECS task-execution role and ECS infrastructure role. The app itself receives no AWS task role. The execution role retrieves the database secret; the browser receives only Supabase's public key.
- `iam/operator-policy.json` is the concrete deployment policy, not a prose permission list. It is scoped to the named resources, Ohio and specific passed roles. AWS's ECS infrastructure managed policy is attached only to the ECS-trusted infrastructure role. That managed policy has broader service-managed infrastructure permissions; its permissions are maintained by AWS and are not claimed to be an immutable custom least-privilege policy.
- `iam/static-check.json` records checks of action names and ARN resource types against AWS's current public service-reference JSON. This is not live IAM simulation or proof of deployment success.
- The cloud build runs frontend tests/build and core backend tests before producing the image. GPU worker tests and Postgres integration checks remain separate. Source packaging excludes environment files, private photos and weights. The image is pinned by digest for deployment.

## Administrator step

Review the JSON files in `iam/`. An existing account administrator runs, from the repository root:

```sh
python3 deploy/ecs/bootstrap_iam.py --profile ADMIN_PROFILE
python3 deploy/ecs/bootstrap_iam.py --profile ADMIN_PROFILE --apply
```

The first command is a plan. The second creates/configures these exact roles and grants Ben only `sts:AssumeRole` into the deployment role. It does not grant Ben IAM administration. It refuses to change an existing mismatched trust policy. The exact bootstrap actions/resources are in `iam/administrator-bootstrap-policy.json`. Its `iam:PutRolePolicy` and `iam:PutUserPolicy` actions are privileged: the administrator must review the supplied policy contents, because those actions do not enforce the JSON body. Creating the roles requires an administrator with those permissions; those privileges are deliberately absent from the deployment role.

| Role | Trust | Permissions |
|---|---|---|
| `rest-pilot-deployer` | IAM user `Ben` | `iam/operator-policy.json` |
| `rest-pilot-codebuild` | `codebuild.amazonaws.com` | `iam/build-policy.json` |
| `rest-pilot-ecs-execution` | `ecs-tasks.amazonaws.com` | `iam/execution-policy.json` |
| `rest-pilot-ecs-infrastructure` | `ecs.amazonaws.com` | AWS managed `service-role/AmazonECSInfrastructureRoleforExpressGatewayServices` |

Configure the role profile locally after the administrator completes that step:

```sh
aws configure set role_arn arn:aws:iam::620214493890:role/rest-pilot-deployer --profile rest-pilot
aws configure set source_profile default --profile rest-pilot
aws configure set region us-east-2 --profile rest-pilot
```

For CloudShell, upload `output/rest-ecs-iam.zip` (generated by `python3 deploy/ecs/package_admin.py`), then use the administrator console session:

```sh
unzip rest-ecs-iam.zip
cd rest-ecs-iam
python3 bootstrap_iam.py
python3 bootstrap_iam.py --apply
```

This bundle contains the role setup and policies only. It does not contain credentials or customer data. CloudShell uses its administrator session when no `--profile` is given. The deployment remains a separate step after IAM setup.

No access keys or passwords need to be shared in chat.

## Deploy

Use the existing private `backend/.env` and `frontend/.env.local`; the Supabase project URL and public key are read locally. The database URL travels to Secrets Manager through an owner-only temporary JSON file, never command arguments; the file is removed after the call. No customer photos are uploaded by deployment.

```sh
backend/.venv/bin/python deploy/ecs/deploy.py preflight --profile rest-pilot
backend/.venv/bin/python deploy/ecs/deploy.py deploy --profile rest-pilot
backend/.venv/bin/python deploy/ecs/deploy.py status --profile rest-pilot
```

Preflight verifies the account, all three service roles, public subnets in two availability zones, internet-gateway routing and CodeBuild read access before creating any resources. It does not prove every write permission or free-account-plan service eligibility. Deployment configures the private source bucket, ECR and log groups, starts one cloud build, references the database secret, registers the fixed Fargate task and creates/updates the Express service. The defaults are explicitly 1 vCPU/2 GiB, x86-64, port 8000, health path `/rest-api/healthz`, one steady-state task. Rollouts can temporarily run additional tasks. The database advisory lock coordinates account writes/deletion across container overlap.

The script saves resource identifiers in ignored `output/ecs-deployment.json`; it never saves the database connection value there. On an uncertain failure, inspect the existing build/service before retrying; do not start duplicate builds. Existing database secrets are reused and not silently overwritten. Use a separate explicit secret rotation workflow if the database password changes.

Wait for service status `ACTIVE` and use its returned HTTPS endpoint. Configure that exact origin in Supabase Auth Site URL and redirect allowlist (`/#settings`, `/?reset=1#settings`). Then test signup/confirmation, recovery, routines/check-ins after signout/signin, two-account isolation, product suggestions/feedback, real-photo save/compare/download/delete, consent revocation and export. Restrict initial enrollment to invited testers until email delivery, rate limiting and load checks pass. An AWS endpoint existing is not proof those app flows pass.

## Spending and shutdown

The existing $100 initial credit ceiling covers the initial test; no recurring/monthly budget has been authorized. Express Mode bills for Fargate, an Application Load Balancer, logs and other underlying resources. An idle service/load balancer still costs money. Confirm plan eligibility, credit applicability and the intended hosting period before launching. The script does not upgrade the AWS account plan. Budget alerts are not a hard spending cap.

Express Mode has no App Runner pause operation. To end a test and remove its managed service infrastructure, use the Express deletion workflow, inspect the resources retained/shared afterward, and verify charges stop. Deleting the hosted service does not delete Supabase account records. This command is for an explicitly requested shutdown, not automatic deployment cleanup:

```sh
aws ecs delete-express-gateway-service --service-arn arn:aws:ecs:us-east-2:620214493890:service/rest-pilot/rest-progress-pilot --region us-east-2 --profile rest-pilot
```

ECR images, the source bucket, secrets and log groups are separate retained resources and may continue to incur charges.

## Face-model status

The recommendation engine is application code and ships in this CPU service. No trained skin-product outcome model exists. The previously downloaded SDXL/IP-Adapter model creates illustrations; its outputs do not establish product effects and that UI remains absent from this release.

Fargate/Express Mode does not support a GPU. If an illustration research worker is requested separately, use the existing private EC2 GPU staging design in `deploy/aws/`. Current Ohio G/VT quota is zero (verified October 11, 2026); the Fargate On-Demand quota is 12 vCPUs and the default VPC exists. and the earlier account-plan/GPU eligibility, deployment access, budget/shutdown window and actual CUDA benchmark are still unresolved. No GPU instance or face model has been deployed by this workflow.
